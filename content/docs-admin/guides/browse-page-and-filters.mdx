The home page (`/`) is a browse page: pick a library in the navbar (**Sections**, **Blocks**, **Illustrations**, **Isometric**), filter with the index above the grid (**Categories**, **Type** and **Styles**), and open a card to reach its docs page.

Two files drive everything on it. No list of cards or filter values lives in the components:

| File                    | Defines                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| `constants/taxonomy.ts` | The libraries (tabs), and every category, type and style each library's filter index lists      |
| `registry.json`         | The items (cards), each tagged with one or more categories, types and styles from that taxonomy |

<Callout title="Always add this metadata">
  Every item meant for users needs `categories`, plus a `meta` block with
  `library`, `types`, `styles` and `publishedAt`. Every slug must exist in
  `constants/taxonomy.ts` and be listed for the item's library, or `pnpm
  registry:build` fails and names the item and the slug.
</Callout>

## The taxonomy file

`constants/taxonomy.ts` has three parts:

1. **Pools**: `CATEGORIES`, `TYPES` and `STYLES`. Every value that exists, defined once as `slug: { label }`. The slug is what `registry.json` uses; the label is what the filter shows.
2. **`LIBRARIES`**: per library, its tab label, URL slug, result nouns, and which values from the pools its index lists, **in display order**. A value can be listed by several libraries (`dark-mode` is in all of them).
3. **`NAV_LIBRARIES`**: which libraries the navbar shows as tabs, in order. The first is the default.

```ts
export const STYLES = {
  "dark-mode": { label: "Dark mode" },
  minimal: { label: "Minimal" },
  motion: { label: "Motion" },
  // …
};

export const LIBRARIES = {
  templates: {
    label: "Sections",
    slug: "sections",
    categories: ["marketing", "company", "data", "ai", "portfolio", "ecommerce"],
    types: ["hero", "features", "pricing" /* … */],
    styles: ["motion", "dark-mode", "minimal"],
    // …
  },
  // …
};
```

A value a library lists but no item uses yet shows **dimmed and not clickable**. It signals what's coming and keeps the index's layout stable as items land. A group with more than 5 values splits into two columns. A group a library lists nothing for is hidden.

### Common edits

| To…                            | Do this                                                                                                                             |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Add a value                    | Add `slug: { label }` to its pool, then add the slug to each library that should list it                                            |
| Reorder a library's values     | Reorder its array in `LIBRARIES`                                                                                                    |
| Rename a label                 | Change the `label`. Always safe                                                                                                     |
| Rename a slug                  | Change it in the pool, in `LIBRARIES`, **and** in every `registry.json` item that uses it                                           |
| Remove a value                 | Remove it from `LIBRARIES` (and the pool). The build fails if an item still uses it, so fix those items first                       |
| Add a library                  | Add its id to `LibraryId`, an entry to `LIBRARIES`, and the id to `NAV_LIBRARIES`; then a `content/docs/<id>/` folder for its pages |
| Hide a library from the navbar | Remove it from `NAV_LIBRARIES` (Components is defined but hidden this way)                                                          |

Edits to the taxonomy or the registry show up on their own: the home data's cache key includes a hash of both.

## The item fields

```json
{
  "name": "hero-section-02",
  "type": "registry:block",
  "title": "Split product hero",
  "description": "Headline and CTAs on one side, a drawn product panel on the other.",
  "categories": ["marketing"],
  "meta": {
    "id": "SEC-0006",
    "library": "templates",
    "types": ["hero"],
    "styles": ["minimal", "dark-mode"],
    "publishedAt": "2026-09-30",
    "docs": "hero-section",
    "useCases": [
      "SaaS and AI product landing pages",
      "Launch pages that need proof above the fold"
    ]
  },
  "files": [
    {
      "path": "registry/sections/hero-section-02.tsx",
      "type": "registry:block",
      "target": "components/blocks/hero-section-02.tsx"
    }
  ]
}
```

| Field              | Required          | Drives                                                                                                                                   |
| ------------------ | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `categories`       | yes, one or more  | The **Categories** filter group                                                                                                          |
| `meta.library`     | yes               | Which library tab the card is in: a key of `LIBRARIES` (`"templates"` is shown as **Sections**)                                          |
| `meta.types`       | yes, one or more  | The **Type** filter group. It's labelled **Primitives** in Components                                                                    |
| `meta.styles`      | no (can be empty) | The **Styles** filter group                                                                                                              |
| `meta.publishedAt` | yes               | ISO date (`YYYY-MM-DD`). Sorts **Latest**                                                                                                |
| `meta.useCases`    | yes, 2 to 5       | Who it's for, as short phrases. Not a filter: AI agents read it as **Good for**, with the tags. See [Writing for AI agents](/docs-admin/guides/seo-and-ai-agents#writing-for-ai-agents) |
| `title`            | yes               | The card's name. Use the variant's heading on its docs page ("API keys table"), not the page title                                       |
| `description`      | yes               | The card's one-line tagline. It's truncated, so lead with the point and don't repeat the name                                            |
| `meta.docs`        | no                | The docs page the item lives on, when it isn't its own name. See [Variants](#variants-on-one-page)                                       |
| `meta.preview`     | no                | Local fallback screenshot under `public/`. Real card screenshots live on R2: see [Card screenshots](/docs-admin/guides/card-screenshots) |
| `meta.popularity`  | no                | Sorts **Most popular**. Until there's install data, every item counts as 0 and the tab falls back to newest                              |
| `meta.id`          | yes               | The item's permanent **product code**, e.g. `SEC-0006`. Purchases store it. See [Product codes](#product-codes)                          |
| `meta.free`        | no                | `true` makes the item free. Without it the item is **paid**: its source, Copy for AI and install are for buyers only. See [Paid items](/docs-admin/architecture/registry-pipeline#paid-items) |

`meta.types` replaced the old single `meta.section` string. The build rejects `meta.section` and says what to write instead.

Only tag a style the item really has. For example, use `motion` only if it animates, and `dark-mode` only if it has dark styles or uses theme tokens. AI agents read the tags too: a wrong one makes them recommend the item for the wrong site.

## Strict validation

`lib/taxonomy.ts` checks every item with a `meta.library`. It runs at the start of `pnpm registry:build` (so also in `pnpm build` and CI), and again when the home page's data is built. It fails on:

- a `meta.library` that isn't in `LIBRARIES`
- a category, type or style slug that isn't in its pool (typos like `dark_mode`)
- a slug that's in the pool but not listed for the item's library
- no categories or no types
- a missing or malformed `meta.publishedAt`
- a missing or malformed `meta.id`, one with another library's prefix, or one already used by another item
- a `meta.free` that isn't `true` or `false`
- a missing `meta.useCases`, fewer than 2 or more than 5 entries, or an entry that's empty, over 60 characters or ends with a period
- the old `meta.section` field

Each error names the item, the field and the slug, and says which line of `constants/taxonomy.ts` to change.

## Product codes

Every browse item has a product code in `meta.id`: a three-letter library prefix and a four-digit number. Purchases store this code, not the item's name, so an item can be renamed without breaking anyone's purchase.

| Library (`meta.library`) | Prefix | Example    |
| ------------------------ | ------ | ---------- |
| `templates` (Sections)   | `SEC`  | `SEC-0001` |
| `blocks`                 | `BLK`  | `BLK-0001` |
| `components`             | `CMP`  | `CMP-0001` |
| `illustrations`          | `ILL`  | `ILL-0001` |
| `isometric`              | `ISO`  | `ISO-0001` |

`TPL` is kept for full-page templates, a separate product to come. The prefixes live in `LIBRARIES[…].idPrefix` in `constants/taxonomy.ts`.

Rules:

- **New item:** take the highest number already used with that prefix in `registry.json`, plus one.
- **Never change a code** once the item is published, even if you rename the item or move it to another library. Someone may have bought it.
- **Never reuse a code.** If an item is removed, its number stays retired.

## How filtering works

- **Within a group, picks widen** (OR): Marketing + Company shows items in either.
- **Across groups, picks narrow** (AND): Marketing + Hero + Motion shows items that have all three.
- The search box narrows further, by name and tagline.
- Each library keeps its own picks, so switching tabs and back keeps them.

## The URL

The active tab and its picks are kept in the URL, so a filtered view can be shared, survives a refresh, and is back after returning from a docs page:

```text
/?library=blocks&category=marketing,company&type=charts&style=motion
```

- `library` is the library's `slug`, left out for the first tab.
- Each group's key is its `param` in `FILTER_GROUPS` (`category`, `type`, `style`).
- Values the library doesn't list, or has no items for, are ignored, so an old link shows a wider view instead of nothing.
- Other params (`utm_*` and so on) are kept.
- The page is prerendered with the default view; a link's filters apply as the page hydrates.

## Where a card links

A card opens `/docs/<meta.library>/<page>`, where `<page>` is `meta.docs` or, by default, the item's `name`.

**A card is only created if that docs page exists.** An item without its MDX page is silently left off the grid (and out of the counts), so a card never leads to a 404. If a new item doesn't show up, check its docs page first.

## Variants on one page

Several items can share one docs page. For example, every hero is on `/docs/templates/hero-section`, one preview below the other. For each extra variant:

1. Set `meta.docs` to the shared page's slug (`"hero-section"`).
2. Add a heading and a preview for it on that page:

   ```mdx
   import HeroSection02 from "@/registry/sections/hero-section-02";

   ## Split with product panel

   <ComponentPreview name="hero-section-02">
     <HeroSection02 />
   </ComponentPreview>
   ```

The card then links to `/docs/templates/hero-section#hero-section-02`. Each preview has its item's `name` as its `id`, so the page scrolls to it. The item gets its own card and its own filters.

## Checklist for a new item

<Steps>

<Step>Write the source</Step>

`registry/<library>/<name>.tsx`. See [Adding a component](/docs-admin/guides/adding-a-component) for the rules.

<Step>Check the taxonomy</Step>

Pick its categories, types and styles from `constants/taxonomy.ts`. If one is missing, add it to the pool and to the library's list. Reuse existing values before inventing new ones: `marketing` and `marketing-pages` would show up as two filters.

<Step>Register it with its browse metadata</Step>

In `registry.json`, add the item with `categories`, `meta.id`, `meta.library`, `meta.types`, `meta.styles`, `meta.useCases` and `meta.publishedAt`, plus `meta.docs` if it's a variant.

<Step>Build the registry</Step>

```bash
pnpm registry:build
```

If a slug is wrong, this fails with the item and slug. Fix it and run it again.

<Step>Add or extend its docs page</Step>

`content/docs/<library>/<page>.mdx`, with a `<ComponentPreview name="<name>">`. For a new page, list it in `content/docs/<library>/meta.json`.

<Step>Add its card screenshot</Step>

Save a 16:10 screenshot, at least 1000px wide, in `public/content/`, then run `pnpm media`. See [Card screenshots](/docs-admin/guides/card-screenshots).

<Step>Check the home page</Step>

On `/`, pick the library, then check that:

- the card shows up and the count is right;
- its values in the index are no longer dimmed, and each of them keeps the card;
- the card opens the right page (and the right preview for a variant).

</Steps>

## More like this

Under every docs page that's a browse item, a "More like …" section (for example "More like API keys table") shows up to six other cards from the same library, ranked by the browse tags they share with the page's item(s):

| Shared tag | Points |
| ---------- | ------ |
| A type     | 3      |
| A category | 2      |
| A style    | 1      |

Highest score first, newest first on a tie. Items with nothing in common still fill in after, so the section isn't empty while a library is small. The heading uses the card's name when the page shows one component, and the page title when it holds several variants.

The tags are the same ones the filters use, so **tagging an item well also decides where it shows up as related**. Weights and the limit are in `components/new-hero-section/data/related-items.ts`; the section is `components/docs-related.tsx`. Pages that aren't a browse item (the Components docs, for now) get no section.

## Card screenshots

Card images live on Cloudflare R2 and are managed with `pnpm media`. See [Card screenshots](/docs-admin/guides/card-screenshots) for uploading, replacing and deleting them.

## How it's wired

| File                                                                | Role                                                                                                               |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `constants/taxonomy.ts`                                             | Libraries, pools, each library's listed values, navbar order, URL params                                           |
| `lib/taxonomy.ts`                                                   | Reads an item's values and validates the registry against the taxonomy (also used by `scripts/build-registry.mjs`) |
| `components/new-hero-section/data/registry-home-data.ts`            | Builds each library's index (listed values with counts) and cards                                                  |
| `lib/media.ts`, `constants/media.ts`, `content/media-manifest.json` | Card screenshots on R2: the manifest, its validation and each card's `srcSet` (written by `scripts/media.mjs`)     |
| `components/new-hero-section/data/get-home-data.ts`                 | Caches the result. The key hashes the registry and the taxonomy, so edits show up on their own                     |
| `components/new-hero-section/browse/browse-shell.tsx`               | Owns the active tab and every library's picks, and keeps them in the URL                                           |
| `components/new-hero-section/browse/browse-url.ts`                  | Reads and writes the URL                                                                                           |
| `components/new-hero-section/browse/browse-filters.tsx`             | The selection store, and the OR/AND matching                                                                       |
| `components/new-hero-section/browse/browse-index.tsx`               | The filter index above the grid                                                                                    |
| `components/new-hero-section/browse/browse-feed.tsx`                | Filters and orders the cards on the client                                                                         |

In code, each item carries tags like `categories:marketing`, `types:hero` and `styles:minimal`.

<Callout title="Changing the data's shape">
  Editing `registry.json` or `constants/taxonomy.ts` needs no cache bump.
  Changing the `HomeData` type does: bump `HOME_DATA_VERSION` in
  `get-home-data.ts`, or pages keep the old shape from the Data Cache.
</Callout>
