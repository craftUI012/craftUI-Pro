<Callout title="Every text you write follows one guideline">
  The descriptions, use cases, tags, doc comments and card screenshot are what
  Google and AI agents know about the item. Write them to [Writing for AI
  agents](/docs-admin/guides/seo-and-ai-agents#writing-for-ai-agents). When an
  AI adds the item for you, have it read that section and this page first,
  and match an existing item's Markdown, such as
  `/docs/templates/feature-sphere-section.md`.
</Callout>

## At a glance

### 1. Write the component

Create `registry/sections/pricing-section.tsx` (a block goes in `registry/blocks/`).

- **Imports:** only npm packages, `@/lib/utils` or shadcn primitives (`@/components/ui/*`).
- **Breakpoints:** plain `sm:`/`md:`/`lg:`/`xl:`; no container queries.
- **Props:** a `/** doc comment */` above every prop, and above every field of the types they use, because that becomes the AI-agent docs.

No command yet. Details: [Worked example](#worked-example).

### 2. Register it in registry.json

Add an entry with `name`, `title`, `description` (the **card** text), `files`, `dependencies`, and the browse metadata: `categories`, `meta.id` (next code, e.g. `SEC-0009`), `meta.library`, `meta.types`, `meta.styles`, `meta.useCases`, `meta.publishedAt`. Every category, type and style must exist in `constants/taxonomy.ts`.

- **`meta.useCases`:** 2 to 5 short phrases saying who it's for, in a founder's words: `["SaaS pricing pages", "Developer tools with usage-based plans"]`. AI agents match requests against it. See [Use cases](/docs-admin/guides/seo-and-ai-agents#use-cases).
- **Tags:** only what's true. Agents read them as well as the filters.

Details: [Browse page and filters](/docs-admin/guides/browse-page-and-filters).

### 3. Write its docs page

- **The page:** `content/docs/templates/pricing-section.mdx`, with `title` and `description`. The description is the **search** text: "A shadcn/ui pricing section for … : …", 155 characters or fewer.
- **The menu:** add `"pricing-section"` to `content/docs/templates/meta.json` so it appears in the sidebar.
- **Live preview at device widths:** if the section uses breakpoints, add its name to `LIVE_PREVIEWS` in `constants/live-previews.ts`, and its component to `components/live-preview-components.ts`.

Details: [SEO and AI agents](/docs-admin/guides/seo-and-ai-agents#writing-the-search-description).

### 4. Build the registry

```bash
pnpm registry:build
```

What it does:

1. **Checks your metadata** against `constants/taxonomy.ts`, and stops with the bad value named if anything's wrong.
2. **Builds the install files:** `public/r/pricing-section.json`.
3. **Moves the paid ones** into `registry-paid/`, since every item is paid unless marked free.
4. **Writes the AI-agent reference:** `content/agent-reference.json`, with its props, defaults and comments.
5. **Prints warnings** like `! pricing-section: prop "plans" has no doc comment` or `field "Plan.price" has no doc comment`. Fix any you see and run it again.

Then normalise the formatting of the built files:

```bash
pnpm exec oxfmt registry-paid public/r
```

Details: [Registry pipeline](/docs-admin/architecture/registry-pipeline).

### 5. Check it in the browser

```bash
pnpm dev
```

- **`/docs/templates/pricing-section`:** the preview, at mobile, tablet and desktop widths.
- **`/`:** its card, in the right filters.
- **`/docs/templates/pricing-section.md`:** what AI agents get (At a glance, Install, Usage, Props, Files). [Test it](/docs-admin/guides/seo-and-ai-agents#test-it-before-you-commit) against three requests a founder would type.
- **`/seo-admin` → Page audit:** its row has no red issues. Fix the title or description there with **Edit SEO text**.

### 6. Add the card screenshot or video

Drop the capture into `public/content/`, then run:

```bash
pnpm media
```

It asks which file, proposes a name and asks you to confirm, makes the sizes, uploads them to R2 and updates `content/media-manifest.json`. The same screenshot is the image AI agents see (as a JPEG, linked from the item's Markdown and `llms.txt`), so show the item at its best.

Details: [Card screenshots](/docs-admin/guides/card-screenshots) and [Card videos](/docs-admin/guides/card-videos).

### 7. Check the code

```bash
pnpm typecheck
pnpm check
```

`typecheck` runs the TypeScript compiler and `check` runs lint. Don't run `pnpm fix` on MDX files: it breaks their comments.

### 8. Commit

```bash
git add -A
git commit -m "feat: pricing section (SEC-0009)"
```

The pre-commit hook formats and lints code, and only formats JSON and CSS. Commit `registry.json`, the component, the docs page, `registry-paid/`, `public/r/`, `content/agent-reference.json` and the media manifest together.

### 9. Deploy

```bash
git push
```

Vercel runs `pnpm build`, which runs `pnpm registry:build` again and then `next build`. So the install files and the AI reference are always regenerated from the code. Its sitemap entry, share image, `llms.txt` line and Markdown page all appear on their own.

Details: [Deploying](/docs-admin/guides/deploying).

### In short

Write the component (with prop and field comments), register it with its use cases, write its docs page, all to [the guideline](/docs-admin/guides/seo-and-ai-agents#writing-for-ai-agents), then `pnpm registry:build`, check in `pnpm dev`, run `pnpm media` for the card, and commit. The rest is automatic.

## Worked example

The walkthrough below adds a `status-badge` component. Its library is `components`; the steps are the same for a section or a block.

<Steps>

<Step>Write the component</Step>

Create `registry/components/status-badge.tsx` (its library is `components`; a section goes in `registry/sections/`, a block in `registry/blocks/`, and so on):

```tsx
import { cva } from "class-variance-authority";
import type { VariantProps } from "class-variance-authority";
import type { ComponentProps } from "react";

import { cn } from "@/lib/utils";

const statusBadgeVariants = cva(
  "inline-flex items-center gap-1.5 rounded-full px-2.5 py-0.5 text-xs font-medium",
  {
    defaultVariants: { status: "idle" },
    variants: {
      status: {
        error: "bg-destructive/10 text-destructive",
        idle: "bg-muted text-muted-foreground",
        live: "bg-emerald-500/10 text-emerald-600 dark:text-emerald-400",
      },
    },
  }
);

export type StatusBadgeProps = ComponentProps<"span"> &
  VariantProps<typeof statusBadgeVariants>;

export const StatusBadge = ({
  className,
  status,
  children,
  ...props
}: StatusBadgeProps) => (
  <span
    data-slot="status-badge"
    className={cn(statusBadgeVariants({ status }), className)}
    {...props}
  >
    <span className="size-1.5 rounded-full bg-current" />
    {children}
  </span>
);
```

Rules for registry source:

- Import only from **npm packages**, **`@/lib/utils`**, or **shadcn primitives** (`@/components/ui/*`). Everything else must be declared (see step 2).
- **Never** import site-only modules (`@/hooks/use-feedback`, `@/constants/*`, `@/components/<site-component>`). They don't exist in users' projects.
- Add `"use client"` at the top if you use state, effects, refs or event handlers.
- Style with Tailwind classes and shadcn tokens (`bg-muted`, `text-foreground`) so the component adapts to each user's theme.
- Add `data-slot="<name>"` on the root, following shadcn v4 conventions.
- Put a `/** doc comment */` above **every prop** in the props interface. It's what AI agents read: the registry build copies each prop's type, default and comment into the item's Markdown (see [SEO and AI agents](/docs-admin/guides/seo-and-ai-agents)). A `/* plain comment */` doesn't count.

<Step>Register it in registry.json</Step>

Add an entry to `items`:

```json
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "craftui-pro",
  "homepage": "https://your-domain.com",
  "items": [
    {
      "name": "status-badge",
      "type": "registry:ui",
      "title": "Status Badge",
      "description": "A pill badge with idle, live and error states.",
      "dependencies": ["class-variance-authority"],
      "categories": ["feedback"],
      "meta": {
        "id": "CMP-0001",
        "library": "components",
        "types": ["badge"],
        "styles": ["minimal", "dark-mode"],
        "publishedAt": "2026-10-01",
        "useCases": ["SaaS dashboards", "Status and uptime pages"]
      },
      "files": [
        {
          "path": "registry/components/status-badge.tsx",
          "type": "registry:ui",
          "target": "components/ui/status-badge.tsx"
        }
      ]
    }
  ]
}
```

- `name` **must match** the filename (`status-badge.tsx`). The docs site looks up source by this name.
- `dependencies` lists npm packages the CLI installs for users.
- If you depend on shadcn primitives, add `"registryDependencies": ["button", "tooltip"]`.
- If it needs **a helper file** (shared CSS, a sub-component), ship that file inside the item: add it to `files` with the same target folder and import it relatively (`./avatar-grid`). Several items can ship the same file. A bare name in `registryDependencies` (`"avatar-grid"`) is looked up on **ui.shadcn.com**, not here, and fails to install.
- Only depend on **another item in this registry** when it's a real component in its own right, and then by its full URL: `"registryDependencies": ["https://your-domain.com/r/other-thing.json"]`.
- List every npm package the files import in `dependencies`. The CLI installs only what's listed.
- `categories` and `meta` put it on the home page and in its filters. Every field is covered in [Browse page and filters](/docs-admin/guides/browse-page-and-filters).
- Every category, type and style must be in `constants/taxonomy.ts` and listed for the item's library. This example uses `feedback` and `badge`, which aren't there yet: add `feedback: { label: "Feedback" }` to `CATEGORIES` and `badge: { label: "Badge" }` to `TYPES`, then list them in `LIBRARIES.components`. Otherwise `pnpm registry:build` fails and names the slug.
- Full field list: [registry.json reference](/docs-admin/reference/registry-json).

<Step>Build the registry</Step>

```bash
pnpm registry:build
```

Check that `registry-paid/status-badge.json` exists (or `public/r/status-badge.json`, if you marked it `"free": true`) and that its `files[0].content` contains your code. New items are paid by default.

The build ends by writing the item's agent reference (`content/agent-reference.json`). Read its output: a line like `! status-badge: prop "status" has no doc comment` means agents would see an empty description. Add the comment and build again.

<Step>(Optional) Add a demo</Step>

If you create `examples/status-badge.tsx`, the preview shows **that file's source** instead of the raw component:

```tsx
import { StatusBadge } from "@/registry/components/status-badge";

export default function StatusBadgeDemo() {
  return (
    <div className="flex gap-2">
      <StatusBadge>Idle</StatusBadge>
      <StatusBadge status="live">Live</StatusBadge>
      <StatusBadge status="error">Error</StatusBadge>
    </div>
  );
}
```

<Step>Write the docs page</Step>

Create `content/docs/components/status-badge.mdx`:

````mdx
---
title: Status Badge
description: A pill badge with idle, live and error states.
---

import { StatusBadge } from "@/registry/components/status-badge";

<ComponentPreview name="status-badge">
  <div className="flex gap-2">
    <StatusBadge>Idle</StatusBadge>
    <StatusBadge status="live">Live</StatusBadge>
    <StatusBadge status="error">Error</StatusBadge>
  </div>
</ComponentPreview>

## Props

| Prop     | Type                          | Default  |
| -------- | ----------------------------- | -------- |
| `status` | `"idle" \| "live" \| "error"` | `"idle"` |
````

- `<ComponentPreview name="status-badge">` renders the children (the live preview), then the highlighted source for `status-badge`.
- **Sections with breakpoints:** the preview toolbar's phone and tablet buttons only narrow the box, so `sm:`, `md:`, `lg:` and `xl:` classes (which follow the browser window) wouldn't switch. For an item like that, add its name to `LIVE_PREVIEWS` in `constants/live-previews.ts` and its component to `components/live-preview-components.ts`. Its preview then runs in an iframe of `/preview/<name>` at a real device width (390 phone, 834 tablet, 1440 desktop, scaled to fit), so it lays out exactly as on that device, and the MDX children aren't shown.
- `<InstallCommand name="status-badge" />` renders the install command with npm, pnpm, yarn and bun tabs. The domain comes from `NEXT_PUBLIC_SITE_URL`, so never hard-code it in a code block. See [Changing the domain](/docs-admin/guides/changing-the-domain).
- Usage examples should import from `@/components/ui/<name>`, **the path in the user's project**, not `@/registry/...`.
- The front matter's `description` is the page's **search description** (Google, share cards, AI answers), not the card text. Write it as an answer to "I want to build …": what it is, who it's for and the problem, then how it solves it, in 155 characters or fewer. See [SEO and AI agents](/docs-admin/guides/seo-and-ai-agents#writing-the-search-description). You can edit it later from `/seo-admin`.

<Step>Add it to the sidebar</Step>

In `content/docs/components/meta.json`:

```json
{
  "title": "Components",
  "pages": ["index", "status-badge"]
}
```

Pages not listed in `pages` don't appear in the sidebar or in `<ComponentsList />`.

<Step>Verify</Step>

```bash
pnpm dev
```

- `/docs/components/status-badge` shows the preview and source.
- `/docs/components` lists it.
- On `/`, **Components** shows its card, and its category, primitive and style filters keep it.
- `http://localhost:3000/r/status-badge.json` returns the JSON.
- `http://localhost:3000/docs/components/status-badge.md` shows **At a glance, Install, Usage, Props and Files**, with every prop described.
- `/seo-admin` → **Page audit**: its row has no issues (title and description within their limits).
- In a scratch Next.js app with shadcn initialised, run `npx shadcn@latest add http://localhost:3000/r/status-badge.json`.
- Run `pnpm check && pnpm typecheck`.

</Steps>

## Other item types

| Type                                | Use for                                               | Default install folder               |
| ----------------------------------- | ----------------------------------------------------- | ------------------------------------ |
| `registry:ui`                       | A single primitive-style component                    | `components/ui`                      |
| `registry:component`                | A composite component                                 | `components`                         |
| `registry:block`                    | A multi-file section (for example, a pricing section) | `components` (set `target` per file) |
| `registry:hook`                     | A React hook                                          | `hooks`                              |
| `registry:lib`                      | Utilities                                             | `lib`                                |
| `registry:page`                     | A route file (must set `target`)                      | the `target` path                    |
| `registry:file`                     | Any other file (must set `target`)                    | the `target` path                    |
| `registry:style` / `registry:theme` | CSS variables and design tokens                       | merged into the user's CSS           |

Multi-file example:

```json
{
  "name": "pricing-block",
  "type": "registry:block",
  "registryDependencies": ["button", "card"],
  "files": [
    {
      "path": "registry/blocks/pricing.tsx",
      "type": "registry:component",
      "target": "components/pricing/pricing.tsx"
    },
    {
      "path": "registry/blocks/use-billing.ts",
      "type": "registry:hook",
      "target": "hooks/use-billing.ts"
    }
  ]
}
```

<Callout title="Nested files and the docs lookup">
  `lib/registry.ts` shows the item's **first** file in `registry.json`, so
  list the main file first. To show another file of the item, pass `src`:
  `<ComponentSource src="registry/blocks/use-billing.ts" title="use-billing.ts" />`.
</Callout>

## Renaming or removing the placeholder

`your-component` is referenced in:

- `registry/components/your-component.tsx`
- `registry.json`
- `public/r/your-component.json` (delete it; the build won't remove stale files)
- `content/docs/components/your-component.mdx` and `content/docs/components/meta.json`
- `app/(app)/build-landing-pages-ui-library/page.tsx` (imports `YourComponent` for the landing page showcase)
- `lib/agent-discovery/site-agent-skill.ts` (install example)
